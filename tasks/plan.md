# Implementation Plan: Poker CRM

## Overview

Персональный локальный веб-кабинет для покерной бухгалтерии одного пользователя: румы, балансы/сессии, транзакции (депозит/вывод/перевод), турниры и статистика (график профита как SharkScope + календарь активности). Все деньги в USD с заморозкой курсов на дату; курсы — PokerDom (headless-Chromium) и open.er-api.com.

## Architecture Decisions

- **Монорепо**: `client/` (React 19 + Vite 8 + Tailwind 4) + `server/` (Fastify 5 + `node:sqlite`). Dev — два порта (Vite 5173 + API 3001); prod single-port — сервер раздаёт собранный фронт и API.
- **SQLite**: простой локальный старт, тянет сотни тысяч турниров. `node:sqlite` (`DatabaseSync`) синхронно → нет гонок.
- **Деньги**: храним в минимальных единицах нативной валюты (копейки/центы) + код валюты. В USD конвертируем по курсу, замороженному на дату записи. Никаких float.
- **Парсинг PokerDom**: Playwright headless при старте сервера и при устаревании >12ч. Провал → персистентное уведомление в БД, показывается на сайте, пока пользователь не закроет.
- **Сессия = календарный день**: баланс-записи группируются по дате; профит по руму = дельта баланса − (приход − уход), транзакции в профит не входят.
- **Турниры — детализация сессии**: сумма профитов турниров должна сходиться с профитом рума; расхождение >5% → предупреждение + варианты (баланс / турниры / казино).
- **UI**: тёмный минималистичный, скиллы `frontend-design` и `emil-design-eng` применяются в задачах UI.
- **Шаблоны румов**: «Покердом»/«RedStar» привязывают рум к источнику курса (`rate_source`: pokerdom | er-api), НЕ задают валюты — их выбирает пользователь (только RUB/USD/EUR); конверсия в USD идёт по паре валют замороженным на дату курсом.
- **Стек (фактический)**: React 19 + Vite 8 + Tailwind 4, Fastify 5 + `node:sqlite` (не better-sqlite3), миграции v1..v28 (user_version=28).
- **Закрытие дня = атомарно с импортом**: все способы закрыть день (кнопка «Списать» в «Транзакциях», «Списать на казино» в попапе импорта, `writeoffCasino` внутри батча, standalone `/writeoff-casino`) идут через одно ядро `applyCasinoWriteoff` в `services/tournaments.ts`. Попап шлёт ОДИН `POST /tournaments/bulk` с флагом `writeoffCasino` — casino-транзакция пишется в той же транзакции, что и турниры, поэтому «турниры сохранены, день открыт» невозможно. Несводимый день откатывает батч целиком.
- **Списание = casino-транзакция, а не маркер (v26, 2026-10-05)**: остаток дня `R = S − T − X` пишется обычной casino-строкой в USD через `recordCasinoPnl` (прямой INSERT **без** балансовых legs: баланс дня уже измерен и остаток в нём уже учтён, поэтому обычный `createTransaction` день не закрывает — он двигает баланс и `R` не меняется). Таблица `casino_writeoffs` удалена, «умная пружина» (`isCasinoWriteoff`) убрана. Следствия: `R = 0` → строки нет (повторное «Списать» — no-op, чужой комментарий не перетирается); ретроспективный импорт турниров или правка баланса (в т.ч. другого дня) снова открывают день с честным остатком, которому можно выписать отдельную casino-строку. Проверено на копии живой БД: миграция открывает ровно один день (GG 2026-09-23), и он был открыт и до неё.
- **Сверка только по ручному балансу** (решение пользователя 2026-09-29): авто-интерполированный баланс (`source='auto'`) — это carry-forward, который играет транзакции, но НЕ результаты турниров, поэтому `S = X` и `R ≡ −T` — 100% фантом. Пока баланс за день не записан вручную, расхождение не считается (`flagged=false`, `remainderUsd=null`, `blank` с причиной), день не попадает в «Транзакции», а write-off/adjust отвечают 400. Много-дневный импорт НЕ расширяет списание на чужие даты: чтобы день стал сверяемым, нужен реальный баланс за него.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Сайт PokerDom меняет вёрстку / долго грузится / антибот | High | Робастный wait + ретраи, валидация значения, персистентное уведомление (пользователь увидит и разберётся) |
| Ошибки денежной математики | High | Юнит-тесты на все деньги (профит, конверсия по дате, расхождение) |
| Курс «заморожен» неверно (по дате/таймзоне) | Med | Единый часовой пояс дня, курс хранится по дате, тесты границ дней |
| Объём данных (сотни тысяч турниров) | Med | Индексы на (room_id, date), агрегаты в SQL, графики по суммарным рядам |
| SQLite блокировки | Low | Single-user, синхронный `node:sqlite` (`DatabaseSync`), `PRAGMA synchronous = NORMAL` |

## Open Questions

- «Вне игры» (деньги на бирже/кошельках) — включено по умолчанию как вычисляемая строка в дашборде.
- **«Умное распределение» расхождений при загрузке пачки турниров** (2026-10-11, план пользователя на
  будущее): пачка турниров + один актуальный баланс → авто-разнесение по реальным датам из отчётов +
  сведение расхождений без ручной правки пропущенных дней. Частный случай Класса A (турнир приехал
  в день, уже закрытый списанием): предлагать «снять с прежнего списания» (уменьшить его), а не новую
  casino-строку — она даёт двойной счёт (списание вычислялось при неполном `T`).
