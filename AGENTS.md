# Project Map: Poker CRM

Персональный локальный веб-кабинет для покерной бухгалтерии одного пользователя:
румы, балансы/сессии, транзакции (депозит/вывод/перевод), турниры, статистика
(график профита как SharkScope + календарь активности). Тёмный минималистичный UI,
подписи на русском.

## Tech Stack

- **Monorepo**: npm workspaces `client/` + `server/` (root `package.json`).
- **Client**: React 19, Vite 8, Tailwind CSS 4, TypeScript 6. Без UI-библиотек.
  Графики статистики — **Recharts** (по требованию пользователя; кастомный SVG удалён).
  Календарь активности — кастомный (не Recharts).
  Дневник дневника: **Tiptap** v3 (минимальный набор: `@tiptap/react`, `@tiptap/core`, `@tiptap/pm`,
  `extension-document/paragraph/text/bold/italic/underline/highlight/hard-break/history/placeholder`,
  `@tiptap/extension-text-style` → `TextStyle`/`FontSize`) —
  rich text в заметках целей: размер шрифта 8–20px и многоцветный пастельный маркер (`Highlight.configure({ multicolor: true })`).
- **Server**: Fastify 5 + встроенный `node:sqlite` (`DatabaseSync`, Node ≥22.5; на машине Node 26.3.0).
  Multipart (загрузка ZIP) — `@fastify/multipart`, распаковка — `adm-zip`.
- **Scraper**: Playwright headless Chromium. Fallback на системный Chrome/Edge, если ms-playwright пуст и npx playwright install chromium timeout.
-   **Тесты**: vitest — сервер (`server/tests/*.test.ts`, 31 файл) и клиент (jsdom + `@testing-library/react` + `@testing-library/user-event` в `client`, env `pretendToBeVisual` для rAF-анимаций motion; полифиллы Range/document для Tiptap/ProseMirror в `client/tests/setup.ts`).

| `start.bat` (или `start.ps1`) | умный фон-запуск: проверка портов 3001/5173; не запущены → старт в фоне (hidden cmd, переживает закрытие терминала) + браузер; запущены → меню [1] Перезапустить, [2] Остановить, [3] Вкл/выкл автозапуск, [4] Выйти. ## Architecture

- **Деньги**: храним в минимальных единицах нативной валюты (1/100) + код валюты;
  никаких float. В USD конвертируем по курсу, замороженному на дату записи.
  Валюты румов — только RUB/USD/EUR (allowlist `validateCurrency`).
- **Курсы**: PokerDom (USD→RUB, строка `USD` с `₽`, не первое число) через headless Chromium,
  зеркала перебираются **последовательно** (`scrapeFromMirrors` в `rates/pokerdon.ts`): список —
  `POKERDOM_MIRRORS` (через запятую, из `process.env`, дефолт `https://pd-play-x7wq3.com/poker`,
  затем `https://plk7pokerdom.com/poker`; пустое/мусорное значение → дефолты, дедуп по порядку);
  ошибка одного зеркала (таймаут навигации, `ERR_NAME_NOT_RESOLVED`, страница без блока `USD`,
  неразобранный курс) пишется в лог `[rates] PokerDom mirror unavailable <url>: <причина>`
  и demote-ит только это зеркало; успех на первом ответившем немедленно возвращает курс; когда
  зеркала кончились — одна агрегированная ошибка «Все зеркала PokerDom недоступны (N): url — причина;
  …» (её и показывает уведомление). **Fail-fast**: и навигация, и ожидание блока `USD` ограничены
  30с (`PAGE_TIMEOUT_MS`/`TEXT_WAIT_MS`) — живой замер: все три зеркала отдают курс за 2–3с, поэтому
  зеркало, которое не показало блок за 30с, считается мёртвым (худший случай всего цикла
  2 зеркала × 3 попытки ≈ 6 мин вместо 18); внешний цикл `ATTEMPTS = 3` с бэкоффом 5с/10с сохранён.
  Плюс open.er-api.com (EUR→USD). Refresh при старте и каждые 4 часа.
  **Авто-ретрай**: любой частичный сбой переармит таймер с бэкоффом 30с → 1м → 2м → … → макс 15мин
  (`autoRefresh` в `rates/refresh.ts` — единая точка для старта/интервала/ручного `/api/rates/refresh`),
  полный успех снимает таймер (`cancelRetry`) — транзиентные сбои (сеть не поднялась при включении ПК,
  сбой скрейпа) самоизлечиваются за минуты, а не висят до следующего 4-часового интервала.
  **Grace-период уведомлений**: персистентное уведомление создаётся только после 3 подряд неудач
  одного источника (`NOTIFY_AFTER_FAILURES`, счётчик `consecutiveFailures` сбрасывается успехом) —
  кратковременные сбои не мелькают в баннере; успех → `resolveKind` снимает уже показанное.
  Конверсия: direct → inverted → цепочка через USD;
  на день без курса — fallback на последний известный. Rум привязывается к источнику курса
  из шаблона: `rate_source` (`pokerdom` | `er-api`) — шаблоны «Покердом»/«RedStar» в `templates.ts`,
  детект по названию без жёсткой подстановки валют.
- **Сессия = календарный день** (`lib/date.ts`, единый таймзона дня). Профит рума =
  дельта баланса (в USD по курсу дня) − (приход − уход); транзакции в профит не входят
  (in = amount, out = amount + fee). Переводы — между своими румами: `direction` всегда 'out'
  отправителя, у записи есть `destination_room_id`; поток = две ноги (отправитель −(amount+fee),
  получатель +amount, конвертированный в валюту рума по курсу дня) — обе профит-нейтральны.
  `RoomProfit.source` ('manual' | 'auto') несёт источник баланса дня: без него реконсиляция
  не отличает измеренный баланс от интерполяции (см. правило «только по ручному балансу»).
- **Транзакции**: типы `deposit` | `withdraw` | `transfer` | `casino` (миграция v15 расширила
  CHECK на `transactions.type`). Обычные транзакции требуют `amount > 0`, `casino` — знаковый
  результат (выигрыш `>0`, проигрыш `<0`, ноль запрещён), `fee = 0`, без `destination_room_id`;
  `direction` выводится из знака. Casino — это гейминг-P&L, а не внешний поток: он исключён из
  `flowsUsdRange`/`flowTotals` (`type NOT IN ('transfer','casino')`) и прибавляется к цепочке
  балансов **signed** (`recomputeRoomBalances`); день только с casino — игровой. Списание дня —
  это **обычная casino-транзакция на весь остаток** `R = S − T − X` в USD (`fee = 0`,
  `direction` по знаку), а не маркер рядом с бухгалтерией: `recordCasinoPnl`
  (`services/funds.ts`) пишет её прямым INSERT **без балансовых legs**, потому что баланс дня
  уже измерен и этот остаток в нём уже учтён (обычный `createTransaction` двигает баланс —
  именно поэтому он день не закрывает, `R` не изменился бы). Следствия: день без остатка
  (`R = 0`) не получает строку вообще (повторное «Списать» — no-op, чужой комментарий не
  перетирается), а любая последующая правка — ретроспективный импорт турниров, правка баланса
  этого или другого дня — снова открывает день с честным остатком, которому можно выписать
  отдельную casino-строку. Таблица `casino_writeoffs` (v26) удалена.
- **Авто-подгонка баланса транзакцией** (side-effect-хук в `funds.ts`, миграция v18):
  ручной баланс — это **абсолютный снимок**, `recomputeRoomBalances` его НИКОГДА не пересчитывает
  (`amount`/`currency` берутся как есть и уходят carry-forward). Депозит/вывод/казино/перевод,
  введённый после баланса, двигает текущий баланс через явный хук: `applyBalanceLegs` в
  create/update/delete транзакции вызывает `shiftManualBalanceOnDay(roomId, date, effectUnits, currency)`,
  который сдвигает **только ручную запись ровно на дату транзакции** (`source='manual'`); если её нет —
  ничего не делает, и день обрабатывается авто-интерполяцией (`source='auto'` carry-forward на дату
  транзакции/турнира без якоря). Эффект ноги: `casino` → `amount` (знаковый), `transfer` → `−(amount+fee)`
  (получатель `+amount`), иначе `direction==='in'` → `amount`, иначе `−(amount+fee)`; конверсия — через
  `convertCross` в валюту ручной записи. Update = откат старой формы (−1) + применение новой (+1); delete
  = откат (−1). Двойного счёта нет: правило «только дата транзакции» исключает сдвиг на других днях,
  поэтому сессионный инвариант `profit = delta − (in − out)` сохраняется на всей истории; правки
  идемпотентны (`recomputeAllBalances()` на старте пересобирает только `source='auto'`).
  Колонки `balance_entries.base_amount`/`base_tx_id` (v17) оставлены в схеме, но **мертвы** — код их
  игнорирует, `upsertBalance` их не пишет; v18 восстанавливает `amount = base_amount` для ручных строк,
  которые v17 успел исказить.
- **Logical Day Boundary** (миграция v16, таблица `settings`, ключ `day_start_hour` 0..12, дефолт 0):
  ночная сессия после полуночи не должна рваться на два календарных дня. Роут импорта читает
  `getDayStartHour()` и кладёт в `TournamentParserContext.dayStartHour`; `ggParser` при старте
  турнира раньше этого часа вычитает 1 день из даты (`addDays`), и сессия, начатая в 04:00 18-го,
  пишется на 17-е. Порог строгий (`hour < day_start_hour`), время определяется по строке
  `Tournament started … YYYY/MM/DD HH:MM:SS`; `pokerdomParser` применяет тот же порог к строке
  `DD мес., HH:MM` (хэш при этом считается по ИСХОДНОЙ дате отчёта, поэтому смена настройки
  пере-импортирует турнир в новый день через upsert, а не плодит дубль); исторические строки
  не переписываются — сдвиг только на импорте. UI: шестерёнка в правом углу шапки → модалка
  «Настройки» (`SettingsModal`), селект 00:00–12:00, сохранение через `PUT /api/settings`.
- **Турниры — детализация сессии**: профит турнира = результат − байин (USD по курсу дня);
  GG re-entry (`You made N re-entries and received a total of …`) — байин умножается на `1 + N`
  (в отчёте указан только базовый байин), количество захватывается из строки результата;
  расхождение `|сессия − (турниры + казино)| / max > 5%` → флаг + варианты:
  «Поправить баланс», «Списать на казино» (обычная casino-транзакция на остаток дня), правка строк.
- **Импорт турниров**: единый stateless эндпоинт `POST /api/tournaments/import/:roomId` (распаковка ZIP + парсер в RAM, ответ `{tournaments, successfullyParsed, failures, totalSources}`, в БД НИЧЕГО не пишет) — парсер выбирается из реестра `services/parsers/registry.ts` по шаблону рума (`detectRoomTemplate`), каждый парсер реализует контракт `ITournamentParser` (`services/parsers/types.ts`); нет парсера для шаблона → 501. GG-архив (`ggParser`, `accepts: 'zip'`), текст PokerDom (`pokerdomParser`, `accepts: 'text'`). Сохранение — только через `/bulk` с `imports`
  (`saveDayBatch`): upsert по `(room_id, tournament_id)`, распределение по датам из самих отчётов, ручные строки (модальной даты, `tournament_id IS NULL`)
  заменяются отдельно и импорт не затирают. Несовпадение числа разобранных файлов (`successfullyParsed < totalTxtFiles`) → клиент блокирует сохранение.
   Удаление импортированного турнира — `deleteImportedTournament` / `POST /api/tournaments/delete-import` по `(room_id, tournament_id)` (крестик ✕ в попапе, даже на read-only строках).
  Интерполяция: `recomputeRoomBalances` создаёт авто-запись carry-forward на дату турнира без записи баланса (сессия дня появляется для сверки).
  **Атомарное списание в окне импорта**: `POST /api/tournaments/bulk` принимает `writeoffCasino?: boolean`
  и в той же транзакции (те же `withTransaction`/`recomputeRoomBalances`) зовёт общий write-off-ядр
  `applyCasinoWriteoff` для модальной даты — ровно то, что делает кнопка «Списать» в «Транзакциях»
  (различается только комментарий). Фронт шлёт ОДИН запрос (`api.tournaments.save(..., writeoffCasino)`
  — шестой аргумент, флаг едет в теле), ответ уже содержит закрытый день — второй round-trip
  `/tournaments/writeoff-casino` из попапа убран. Порядок в `saveDayBatch` важен и закреплён тестом:
  сначала строки турниров → `recomputeRoomBalances` → pending-маркер → и только потом `applyCasinoWriteoff`,
  поэтому остаток `R = S − T − X` считается по уже записанному состоянию (в т.ч. транзакции батча).
  Несводимый день (`blank`) → 400 и откат всего батча: сохранять импорт, который пользователь просил
  свести, — не лучшая половина. Эндпоинт `/writeoff-casino` остался (тот же ядро, standalone-вызов).
  **Авто-привязка баланса к датам импорта (без ручных дат — требование пользователя 2026-10-08)**:
  `saveDayBatch` при сохранении с импортами (`deduped.length > 0`) зовёт `reanchorBalanceToBatch`
  в той же транзакции ПОСЛЕ `applyCasinoWriteoff`: `target` = последняя дата батча (даты импортов
  ∪ modal-дата, только если в батче есть ручные строки). Если последняя **ручная** запись баланса
  рума стоит позже `target` (баланс «записал сегодня», форма даты в «Балансах» нет), на ней нет
  турниров рума датой > `target`, в зазоре `(target, дата баланса]` нет транзакций (включая
  casino) — ручной баланс переносится на `target` (auto-строка дня удаляется, затем
  `recomputeRoomBalances(roomId)`), ответ `/bulk` несёт `reanchored: {from, to} | null`.
  Сессия дня баланса при этом исчезает (нет турниров/транзакций — держать нечего), деньги
  попадают в дельту между балансами. Гард-исключения (переноса НЕТ): транзакция в зазоре,
  ретроспективный импорт (турнир рума после `target`), ручной якорь уже на `target`
  (UNIQUE(room_id,date)), ручные строки на modal-дне батча, сейв без импортов (manual-only),
  writeoff-флоу (casino-транзакция modal-дня пишется до проверки → засчитывается как
  «что-то случилось», поведение «Списать» не меняется). Клиент: ответ `save` → `reanchored`,
  `saveThen('adjust')` шлёт `adjustBalance(roomId, saved.reanchored?.to ?? date)` — «Поправить
  баланс» привязывается к новому дню. Тесты — `server/tests/balance-reanchor.test.ts`.
  **Превью моделирует реанкор** (фикс фантомного «Расхождение 100%», 2026-10-09): из
  `reanchorBalanceToBatch` вынесены read-only гарды `reanchorTarget(roomId, batchDates)` —
  единый источник правды, сейв и превью не могут разойтись. `previewDayReconcile` возвращает
  `{reconcile, wouldReanchor: {from,to} | null}` и при `wouldReanchor` считает сверку для целевого
  дня через виртуальную запись `computeRoomProfit({...manual, date: to})` + импорты дня +
  casino-транзакции дня (превью остаётся stateless). Роут `/api/tournaments/preview` отдаёт это
  напрямую; клиент вместо янтарной панели с фантомным процентом показывает нейтральную заметку
  «Баланс {from} будет привязан к {to} при сохранении — сверка выполняется на этот день.».
- **Импорт турниров из текста PokerDom**: тот же stateless `/import/:roomId`, JSON `{text}` (текст из буфера);
  парсер `pokerdomParser` (`pokerdomimport`) разбирает блоки «дата время / название / формат / бай-ин / [Вхождение #N] / строка результата»
  (русские месяцы, `Вхождение #N` → бай-ин ×N, результат/место из последней строки, валюта всегда RUB);
  при `dayStartHour` сдвигает старт раньше порога на предыдущий день (`addDays`, как GG; хэш при
  этом считается по исходной дате отчёта — смена настройки пере-импортирует, а не дублирует);
  `tournamentId` = числовой хэш `name|дата время|базовый бай-ин` (дедуп повтора; два турнира одинакового названия в разное время не конфликтуют);
  сохранение — тот же `/bulk` с `imports`.
  Редактирование в попапе («Сессии» → «Изменить»): для румов с шаблоном `pokerdom` сохранённые турниры дня загружаются
  в **редактируемые строки формы** (в т.ч. hashed-text из БД), их id складываются в `removedImportIds` и отдаются `/bulk`
  (`saveDayBatch(…, removedImportIds)`) — сервер удаляет их ДО upsert, и сохранение конвертирует их в manual-строки без
  дублей; повторная вставка того же текста дедупится против `removedImportIds` (клиент). Для GG-шаблона поведение
  прежнее: hashed-строки — read-only таблица импорта.
  Группировка в «Турнирах» — правило Б (по лимиту бай-ина), т.к. классификация по названию ненадёжна.
- **Ожидание импорта турниров** — персистентный маркер `pending_imports` (миграция v10,
  `UNIQUE(room_id, date)`, на создание пустая — backfill не делался): строка существует ⇔
  на дате `MAX(date)` manual-записи баланса рума НЕТ турниров. Единый пересчёт
  `reconcilePendingImports(roomId)` (`services/pending.ts`, всегда внутри `withTransaction`);
  кошельки маркер не получают: `is_wallet` → существующий маркер снимается и функция выходит.
  ток-пойнты: `upsertBalance`, `deleteImportedTournament`, `replaceDayTournaments`,
  `updateRoom` (пометка кошельком сразу чистит маркер). **Явный сейв = отмашка**: `saveDayBatch`
  при ≥1 записанном турнире (ручная строка или import) снимает маркер рума через
  `clearPendingImport(roomId)` — даже когда архив покрыл только прошлые дни, а баланс лежит на
  новом дне без турниров (играл 1–2-го, 3-го записал баланс «текущего» дня, импортировал вчерашний
  архив → кнопка пропадает); пустой сейв (ничего не записано) откатывается на
  `reconcilePendingImports` и маркер сохраняется. Маркер «взводится» заново следующей записью
  баланса (`upsertBalance`), т.е. цикл «поправил баланс → импортировал → сохранил → играл дальше →
  поправил баланс → снова импортировал» работает: после каждой записи баланса на день без турниров
  кнопка возвращается, после сейва уходит.
  Новый баланс на более поздний день «убивает» старый маркер и пересчитывает новый; авто-записи
  (`source='auto'`) маркер не получают. Кнопка «Заполнить турниры» в «Балансах» держится на
  серверном `pendingImport` из `/api/balances/current`, переживает F5/рестарт (клиентский
  `savedFor` удалён). Пропуск импорта ничего не ломает: маркер — чистая бухгалтерия, не пишет
  в `balance_entries`/`tournaments`/`transactions`; турнирная статистика
  считается только из `tournaments`.
- **Осиротевшие расхождения в «Транзакциях»**: `GET /api/transactions?includeDiscrepancies=1`
  подмешивает дни с `flagged`-расхождением и БЕЗ активного pending-маркера (закрыть можно только
  списанием; диапазон — из фильтров или MIN/MAX дат балансов); `POST /api/transactions/writeoff-discrepancy`
  (обязательный непустой комментарий ≤500, иначе 400) пишет casino-транзакцию через
  `applyCasinoWriteoff` — общее ядро всех способов закрыть день (кнопка «Транзакций», `writeoffCasino`
  батча импорта, standalone `/writeoff-casino`); различаются только валидация комментария и сам текст.
  UI: янтарные строки `<tbody>` с иконкой ⚠, кнопка «Списать» и модал с обязательным комментарием.
  **Правило «только по ручному балансу» (решение пользователя 2026-09-29)**: расхождение
  считается ТОЛЬКО для дней с балансом `source='manual'` (решение пользователя). Запись
  `source='auto'` — это интерполяция carry-forward: она играет транзакции, но НЕ результаты турниров,
  поэтому на таком дне `S = X` и остаток вырождается в `R ≡ −T` — 100% фантом, который нечем
  честно закрыть (измеренного баланса не существует). `computeReconcile` в этом случае отдаёт
  `remainderUsd = null`, `discrepancyPct = null`, `flagged = false` и `blank = 'нет ручного баланса
  за день — сверить не с чем, запиши его в «Балансах»'`; числа (`sessionProfitUsd`,
  `tournamentProfitUsd`, `casinoUsd`) при этом остаются, сравнение — нет. Следствия: в «Транзакциях»
  такие дни не висят (`includeDiscrepancies` пуст), в «Сессиях» вместо янтарного «расхождение»
  показывается нейтральный чип «N турн.», в попапе вместо зелёного «сходится» — причина из `blank`,
  а `writeoff`/`adjust-balance` на такой день отвечают 400 (лечится `upsertBalance`, он переводит
  запись в `manual`, и день начинает сверяться по-настоящему). Порядок проверок в `computeReconcile`:
  нет курса → нет баланса → авто-баланс → расчёт (`casinoUsd` — сумма casino-транзакций дня).
- **Цвет румов**: комната имеет мягкий/кремовый hex-цвет (`rooms.color`, миграция v7,
  allowlist-палитра `ROOM_COLORS` в `client/src/lib/types.ts`, валидация `^#[0-9a-f]{6}$`).
  Имя рума красится этим цветом во всём UI (Румы, Балансы, Сессии, Транзакции, попап турниров);
  новые румы — `#f1f5f9` (slate-100). Существующие румы окрашены по имени: Bybit→slate-100,
  GG→amber-200, PokerDom→emerald-300, RedStar→rose-300 (одноразовый UPDATE в миграции v7).
  Та же палитра и дефолт `#f1f5f9` переиспользованы привычками (`habits.color`, v23):
  на сервере общий хелпер `lib/color.ts` (`DEFAULT_COLOR`/`validateColor`), на клиенте —
  `ROOM_COLORS`/`DEFAULT_ROOM_COLOR` из `lib/types.ts`; имя привычки красится её цветом.
- **Кошельки**: рум может быть кошельком/биржей (`rooms.is_wallet`, миграция v11; миграция
  помечает существующий Bybit по имени без учёта регистра и trim). Кошелёк — владелец баланса
  без турниров: pending-маркер ему не ставится (см. выше), а в игровых вкладках («Турниры»,
  «Статистика», «Сессии») он исключается из списка румов (`rooms.filter(r => !r.isWallet)`);
  в «Балансах» и «Транзакциях» отображается как обычно. UI: чекбокс «Кошелек» и бейдж
  в «Румах».
- **Изоляция MBR** (миграция v14, `tournaments.is_mbr`): «Mystery Battle Royale» (hyper-turbo,
  18-max, только GG) — отдельный формат, изолируемый от MTT серверным scope
  `mbr: 'all'|'mtt'|'mbr'` (`statistics.ts`, `tournamentScope.ts`). **На вкладке «Статистика»
  MBR — такой же покер**: `sessionStats`, календарь (`activityCalendar`) и «Турниров за день»
  (`tournamentCountByDay`, дефолт `'all'`) считают **все** форматы (`'all'`), а `mbrCount` —
  только субнабор-подпись «в т.ч. N MBR» (никаких «MTT-число + отдельно»). Изоляция MBR осталась
  там, где она содержательна: `GET /api/tournaments/summary` отдаёт `{ summary (MTT), mbr }` —
  изолированную сводку (`tournamentMbrKpi`: count, buyin/profit USD, ROI, среднее место `AVG(rank)`
  + `breakdown` по бай-инам `[{ buyin, count, profit, roi, avgPosition }]`; ABI/AFS не нужны —
  всегда 18-max), сводная таблица вкладки «Турниры» и distance-цели (`goals/db.ts collectGoalsFacts`
  — MTT-only). Деньги всегда были всё-инклюзивны: реконсиляция с балансами
  (`tournamentProfitUsd`/`reconcileDay` считают `listDayTournaments` без фильтра), вкладка
  «Сессии» (`sessionsInRange` — gaming-день включает MBR-only дни). Флаг ставится по имени при
  импорте (`isMbrByName` в `services/tournaments.ts`, префикс `mystery battle royale`, зеркалит
  бэкфилл миграции `TRIM(name) LIKE 'Mystery Battle Royale%'`); ручные строки всегда `0`.
  Pending-маркер (`reconcilePendingImports`/`tournamentsExistMap`) считает **все** турниры:
  любой сыгранный турнир, включая MBR-only день, снимает «ожидание импорта»; только distance-цели
  (`goals/db.ts collectGoalsFacts`) остаются MTT-only. Клиент: блок «Mystery Battle Royale» (шапка сыграно/профит/ROI/ср. место + таблица
  разбивки по бай-инам) под основной таблицей
  во вкладке «Турниры» (`client/src/pages/Tournaments.tsx`, тип `MbrSummary`).
- **Монолит**: сервисы содержат бизнес-логику, роуты тонкие (схема Fastify регистрация
  в `app.ts`), БД — один экземпляр `DatabaseSync` (`db.ts`), миграции последовательные
  с `user_version` (сейчас v28). SQLite: `PRAGMA journal_mode = WAL` + `synchronous = NORMAL`
  + `foreign_keys = ON` + `busy_timeout = 5000`; многошаговые записи — только через
  `db.ts#withTransaction` (SAVEPOINT-вложенность `tx_N`).
- **Стабильность/восстановление**: сервер (index.ts) ловит `uncaughtException`/`unhandledRejection`
  → `shutdown(exitCode)`; `shutdown` идемпотентен, закрывает браузер, `app.close()`, затем
  `db.ts#closeDb()` (WAL-checkpoint + закрытие дескриптора), с watchdog 5с на жёсткий выход;
  сигналы `SIGINT`/`SIGTERM`/`SIGBREAK`; `.catch` на все запуски `autoRefresh` (курсы); `pokerdon.getBrowser`
  сбрасывает `browserPromise` при отказе запуска. Клиент: `api.ts` — таймаут запроса 15с (`AbortController`),
  загрузка архива и сейв турниров (`/import`, `/bulk`) — 60с; `ErrorBoundary`-обёртка, polling только через `lib/usePoll.ts` (рекурсивный `setTimeout` — без
  наслоения запросов).
  **Boot Storm (сеть ещё не поднята)**: фатального пути нет — `getDb()`/`recomputeAllBalances()`/
  `createApp()`/`listen()` сети не касаются (единственный `process.exit(1)` — незанятый порт),
  все три источника курсов обёрнуты в `runWithNotification`, поэтому `ENOTFOUND` /
  `ERR_INTERNET_DISCONNECTED` дают `false` + `scheduleRetry()` (30с → … → 15мин), а не throw; уведомление
  появляется лишь после 3 неудач подряд, так что «сеть ещё не поднялась» не мелькает в баннере.
  Оба вызова `autoRefresh` (старт и 4-часовой `setInterval`) с `.catch`, unhandled-rejection на этом
  пути не возникает. Всё ограничено по времени: er-api — `AbortSignal.timeout(15с)` × 3 ретрая,
  PokerDom — 2 зеркала × (30с goto + 30с ожидания блока) × 3 попытки ≈ 6 мин.

## Conventions

- React: функциональные компоненты + хуки, именованные экспорты, без default export.
- Монолит прослеживается: сервисы — чистая логика поверх `getDb()`; роуты тонкие; ошибки — `HttpError`.
- Многошаговые записи в БД — только через `withTransaction` (SAVEPOINT-вложенность; колбэк строго синхронный — runtime-guard бросает на `Promise`); вовлечённые сервисы: balances (recompute), funds (create/update/delete), tournaments (replaceDay), rooms (update + reconcile pending).
- Миграции БД: только через цепочку `MIGRATIONS` в   `db.ts` + бамп `user_version`; тест `db.test.ts` пинит версию (сейчас 28).
- Деньги считаются только в минимальных единицах; конверсия в USD — через `rates/convert.ts`.
- Без комментариев в коде, если не просили. Пользовательские строки — на русском.
- UI: тёмный минимализм; при редизайне применять скиллы `frontend-design` / `emil-design-eng`.

## Boundaries

- Не коммитить секреты; `.env` не трогаем.
- Математика денег всегда покрыта тестами; никаких float.
- Схему БД менять только миграцией + `user_version`, предупреждать пользователя.
- Новые зависимости — только по согласованию с пользователем.
- Остановка сервисов — ТОЛЬКО через `start.ps1` (по PID портов 3001/5173) или точечный `Stop-Process`; **запрещён `taskkill /im node.exe`** — на машине работает ИИ-агент на Node.js.
- Перед завершением задачи: `npm run build && npm run lint && npm test` (и `npm test -w server` отдельно).
- `better-sqlite3` и React 18 в plan.md — устарели (реально `node:sqlite`, React 19); план обновлять при правке задач.
